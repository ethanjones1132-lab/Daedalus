# Memory Phase 4 — Continuity and User Controls Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship scoped operator controls and conservative source revalidation, then demonstrate that accepted memory changes live Jarvis behavior across Sessions and restart.

**Architecture:** Extend the existing Memory view and Session controls using Rust/Tauri commands, native receipts, and persisted Session identity. Add typed statement classification to the native store; treat recalled workspace descriptions as historical context until the existing Tool runtime reads current source. Consume the Phase 2 preparation/invalidation transport and Phase 3 capture, source suppression, and objective continuity; Bun retains its separate TaskRun/tool cache.

**Tech Stack:** Rust 2021, Rust 1.85.0 or later, Tauri 2, SQLite/FTS5 through rusqlite 0.32, React 19, TypeScript, Vitest/Testing Library, Bun; existing Tool runtime/evidence machinery and inference backends. No new persistence service, embedding dependency, verifier, or UI framework.

**Spec:** `docs/superpowers/specs/2026-10-04-memory-four-phase-design.md`; `docs/CURRENT_ROADMAP.md`, priority #1. Read completed Phase 1 scoped foundation, Phase 2 live recall, and Phase 3 safe capture plans before execution.

## Global Constraints

- Rust/Tauri's native memory engine and App SQLite database remain the durable memory authority. Bun consumes bounded recall context and retains its distinct TaskRun/tool-context cache; it must not introduce a second writable durable memory store.
- Agent identity comes from the persisted Session/Agent relationship. Project scope is an explicit, validated workspace binding. Scope selection is separate from filesystem authorization.
- Existing unscoped records are preserved by additive migration. They do not become automatically shared across projects or Agents. Make any rescoping deliberate and inspectable.
- User-wide knowledge is explicitly scoped; sharing across Agents is an explicit policy, never a wildcard fallback.
- Filter Agent/project scope, status, expiry, and tier before ranking/limiting recalled entries.
- Recalled text is data, not authority. It cannot grant filesystem access, change Permission policy, or activate prompt deltas or skills.
- Preserve current FTS-based retrieval for the first slice. Add semantic retrieval only if the acceptance scenarios establish a need.
- Recall limits are at most five entries, 4,000 Unicode scalar values for the full memory block including framing, and 600 scalar values per item. The complete block must also fit the existing model context budget; omit lowest-ranked items if necessary.
- Unconsumed preparations expire after 120 seconds; consumption begins the turn and does not impose a new inference deadline.
- Do not persist recalled blocks in chat history, compaction summaries, TaskRun discovered facts, or reusable tool caches. Each new turn prepares fresh context.
- Already-started turns retain their snapshot; the following turn reflects the mutation. Registering a preparation does not grant workspace access.
- Distinguish normative user constraints from descriptive workspace facts. Fresh source can invalidate a remembered observation; it must not silently override an accepted user requirement.
- Retrieval failures permit an ordinary turn with an observable memory status. Write failures cannot produce a confirmed save receipt.
- Keep the existing native housekeeping helper's skill mutation, prompt deltas, and unrelated learning behaviors outside this priority.
- Implement phases sequentially. Earlier phases must pass their own gates before this phase starts; this plan does not postpone their tests or repair their core contracts by inventing alternatives.
- This is a documentation-only plan. Every command below is a future implementation/validation command. No product tests, toolchain installation, build, live demonstration, or commit was performed while writing it.

## Review Focus

1. An operator selects another Session while a list, mutation, or receipt read is pending: old results must not render under the new Agent/project; Task 3 and Task 4 pin this race.
2. New Session for the same project and a deliberate second Agent must retain the selected native identity without sharing private context; Task 1 and Task 6 pin this behavior.
3. An inactive/superseded/expired legacy entry is restored or adopted: inspection remains possible, but the UI cannot promise recall eligibility; Task 3 pins receipt and eligibility distinctions.
4. A file changes behind a warm TaskRun/tool cache, or reads are denied: stale descriptions cannot satisfy current-source evidence, and accepted user requirements remain intact; Task 5 pins both cases.
5. A disconnect, ambiguous mutation response, or replayed terminal event occurs: the UI must show unavailable/pending until a native receipt confirms the result, without a second logical operation; Tasks 3, 4, and 6 pin this behavior.

## Earlier Contracts Consumed Without Renaming

Phase 1 scoped requests have one `request` argument. They use `session_id`, `ScopeSelector {kind:project|agent|user}`, `MemoryDraft {title,content,tags,category,expires_at,review_after}`, and required `expected_revision` for mutation of existing rows. No UI fields may claim Agent ownership, provenance, verification, or project scope. Categories remain `general|user|feedback|project|reference`; content remains at most 4096 UTF-8 bytes.

| Command | Request fields | Native response |
|---|---|---|
| `memory_bind_session_workspace` | `session_id, workspace_root:string|null` | `MemoryScope` |
| `memory_scoped_save` | `session_id, selector, draft` | `MutationResult` |
| `memory_scoped_read` | `session_id, selector, id` | `ScopedMemoryEntry` |
| `memory_scoped_list` | `session_id, selector, include_inactive` | `ScopedMemoryEntry[]` |
| `memory_scoped_update` | `session_id, selector, id, expected_revision, draft` | `MutationResult` |
| `memory_scoped_restore` | `session_id, selector, id, expected_revision` | `MutationResult` |
| `memory_scoped_recall_preview` | `session_id, query, options:{limit,include_user_scope}` | `RecallPreview` |
| `memory_adopt_legacy` | `session_id, selector, id, expected_revision` | `MutationResult` |

`MutationResult {memory,store_revision,changed}` is an atomic native result, not assistant text. `ScopedMemoryRecall {memory,score,matched_terms,stale}` preserves selection/ranking metadata. `RecallPreview` is a hypothetical query result; it is never labeled “used in this turn.”

Phase 2: `memory_prepare_turn({request:{session_id,turn_id,user_message_id,include_user_scope:false}})->MemoryTurnPreparation`; `memory_sync_turn({request:{session_id,turn_id}})->MemoryTurnDiagnostic`; `memory_turn_diagnostic({request:{session_id,turn_id}})->MemoryTurnDiagnostic` reads persisted metadata. Preparation IDs are opaque. Native persisted turn context owns immutable source message/Agent/project and validates registration with the private Native-to-Bun capability. The UI supplies no envelope or memory text. `MemoryTurnPreparation {turn_id,preparation_id:string|null,status}` remains opaque. `MemoryTurnDiagnostic {turn_id,session_id,scope,store_revision,selected:PreparedMemorySelection[],applied_selected_ids:string[],state,recall_status,error_code:string|null,terminal_status}` distinguishes prepared candidates from actual injection. `PreparedMemorySelection {id,revision,scope,authority_kind,source_session_id:string|null,source_message_ids:string[],source_run_id:string|null,verified_at:string|null,stale}` gains only the additive classification below. State values are `prepared|registered|started|terminal|invalidated|expired|unavailable|unterminated`; recall status values are `ready|empty|unavailable|retrieval_failed|registration_failed|expired|invalidated|scope_mismatch|already_consumed|budget_omitted|applied`. No raw block is exposed in diagnostics.

Phase 3:

| Command | Request fields | Native response |
|---|---|---|
| `memory_capture_turn` | `session_id, turn_id` | `CaptureReceipt` |
| `memory_capture_receipts` | `session_id, turn_id` | `CaptureReceipt|null` |
| `memory_scoped_correct` | `session_id, selector, id, expected_revision, draft, operation_id` | `CorrectionResult` |

`CorrectionResult {previous,replacement,store_revision,changed}` tombstones previous and links replacement by `supersedes_id` atomically. `ForgetResult {memory,store_revision,changed,suppressed_message_ids}` suppresses prompt-source spans and derived summaries without deleting the operator-visible transcript. Restore uses Phase 1; old suppressed source remains neutral, while fresh recall may supply the deliberately restored eligible entry.

`CaptureReceipt {turn_id,session_id,terminal_status,operations,store_revision,continuity_revision,saved_count,pending_count}` has `terminal_status:completed|partial|cancelled|failed|unterminated|null`. Each operation is `{operation_id,status:saved|forgotten|corrected|pending|blocked,memory_id:string|null,replacement_id:string|null,reason_code:string|null}`. Null means no receipt was read, never a confirmed zero saves. Phase 3 owns idempotent replay semantics and the generic `verified_observation` rejection.

`SessionContinuity {session_id,active_objective:ActiveObjective|null,latest_turn_id:string|null,revision}` uses `ActiveObjective {text,source_message_id,source_turn_id:string|null,depends_on_memory_ids:string[]}`. Native validates message ownership and an exact objective substring. Other turns preserve the active objective; only explicit objective controls/commands replace or clear it.

## Phase 4 Additive Spec Extension: Statement Meaning and UI Compatibility

This section defines the Phase 4 statement-classification addition to the earlier frozen store/wire contracts. Task 1 adds trusted bound-project candidate resolution, and Task 5 adds current-read availability metadata to the authenticated runtime receipt/native diagnostic; these are the only other additive extensions and neither grants permissions nor establishes automatic verified observations. Keep `MemoryDraft` unchanged. Add `MemoryStatementKind = normative_constraint|descriptive_fact|unknown` with snake_case serialization in native `contracts.rs` and shared `memory-contract.ts`.

- Add `memory.statement_kind TEXT NOT NULL DEFAULT 'unknown'`, checked against these three values, and `statement_kind` on `ScopedMemoryEntry`. Migration preserves all old content/provenance and classifies existing records as unknown; do not infer meaning from titles/categories or automatically promote old sources.
- Add optional `statement_kind` to scoped save/update/correct request DTOs. Missing save kind means unknown; missing update/correction kind preserves the prior kind. Existing caller payloads remain valid. Classification and content mutation commit in the same transaction/event; correction inherits the prior kind unless the operator deliberately supplies another.
- Add `memory_scoped_classify({request:{session_id,selector,id,expected_revision,statement_kind}})->MutationResult` for changing meaning without rewriting content or provenance. It uses scoped ownership/revision validation and a before/after event. Invalid kind or cross-scope ID changes nothing. Same-kind classification is a native no-op (`changed:false`). Increment row/store revisions on a real change and invoke Phase 2 invalidation.
- Future Phase 3 capture source `explicit_constraint` initializes normative_constraint; `explicit_remember` and `explicit_decision` initialize unknown. Do not infer every decision is a requirement. Accepted descriptions explicitly classified by the operator remain `user_statement`/`manual`; generic automatic `verified_observation` remains unsupported until trusted runtime evidence admission exists.
- Normative requirements remain effective user constraints even when current code contradicts them. Unknown is conservative: current evidence can show a conflict, but cannot silently rewrite the memory or treat it as an obsolete requirement. Descriptive project facts need current-source evidence before being used to make claims or changes about today's workspace.
- Update native serialization, Bun envelope/response validators, and UI scoped fixtures together. UI decoders accept a missing response kind as unknown for older native responses; malformed supplied values produce unavailable/error. Add `statement_kind` to native `PreparedMemorySelection`/Bun wire selection; missing old persisted selected JSON uses unknown. Keep prepared envelope schema_version=1 as an additive field, with current owned native/Bun processes rebuilt together; old registrations are gone on restart. Bun requires the field in newly registered native envelopes after this phase; it never obtains classification from inference or arbitrary `/chat/stream` fields.
