# Memory Phase 3 — Safe Capture Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Capture explicit accepted knowledge, correct and forget it safely, and preserve the active objective through side questions using native transactional receipts tied to the actual Session turn.

**Architecture:** Rust reads the immutable user-message/scope record prepared in phase 2 and privately synchronized Bun lifecycle observations. Compose phase 1 savepoints with an operation ledger, audit events, supersession, source-message suppression, and structured Session continuity. Bun keeps its separate TaskRun/tool cache; assistant text and run success cannot establish durable factual authority.

**Tech Stack:** Existing Rust 2021, Tauri 2, rusqlite 0.32, serde, chrono, Phase 2 SHA-256 utility, Bun/TypeScript, React/Vitest. No second database, verifier, embedding dependency, or skill promotion.

**Spec:** `docs/superpowers/specs/2026-10-04-memory-four-phase-design.md`; `docs/CURRENT_ROADMAP.md`, priority #1. Prerequisites: completed phase 1 scoped foundation and phase 2 live recall plans, including their frozen interfaces.

## Global Constraints

- Rust/Tauri's native memory engine and App SQLite database remain the durable memory authority.
- Agent identity comes from the persisted Session/Agent relationship. Project scope is an explicit, validated workspace binding. Scope selection is separate from filesystem authorization.
- Existing unscoped records are preserved by additive migration. They do not become automatically shared across projects or Agents.
- Recalled text is data, not authority. It cannot grant filesystem access, change Permission policy, or activate prompt deltas or skills.
- Define one unique turn identity shared by UI, Native surface, Bun stream, and capture receipts. Do not assume a model run ID exists for every direct answer or failed turn.
- Memory capture must distinguish explicit user facts, accepted decisions/corrections, verified observations, and assistant proposals. Assistant prose alone cannot become an accepted durable fact.
- Retrieval failures permit an ordinary turn with an observable memory status. Write failures cannot produce a confirmed save receipt.
- Deletion and correction affect the next turn immediately. Do not reuse a persisted or compaction-pinned memory block after its source is invalidated.
- Keep the existing native housekeeping helper's skill mutation, prompt deltas, and unrelated learning behaviors outside this priority.
- Phase 1's 4096 UTF-8 byte content limit and accepted categories apply. Any new continuity prompt data shares phase 2's complete 4,000 Unicode scalar budget; each objective excerpt is at most 600 scalars.
- Implementation is sequential after phases 1–2. All validation commands below are future work; planning performed no dependency installation, product tests, commits, or runtime demonstration.

## Review Focus

1. A vague “yes,” quoted directive, hypothetical decision, or assistant suggestion must not become accepted knowledge; Task 2 tests exact admission and ambiguous acceptance.
2. An interrupted or missing-terminal stream followed by terminal replay must neither duplicate capture nor upgrade assistant authority; Tasks 3 and 6 test every lifecycle and conflict.
3. Correction/event/ledger failure must leave the old record active and the new record absent; Task 4 injects each failure within the outer savepoint.
4. Forgetting must not resurrect content through the original memory-control message, old compaction, cached conductor context, or Session summary; Task 5 tests future prompt serializers and invalidation failures.
5. An ordinary side question, correction, cancellation, or review must preserve the active objective; Task 6 pins native continuity and Bun TaskRun behavior.

## Admission, Lifecycle, and Replay Rules

The first slice's deterministic grammar recognizes only an entire trimmed user message, case-insensitive in the fixed prefix, with nonempty payload: `Remember: <text>`, `Remember that <text>`, `Constraint: <text>`, `Decision: <text>`, `Correct memory <id>@<revision>: <text>`, `Forget memory <id>@<revision>`, and `Accept memory proposal <id>`. Capture source values are respectively `explicit_remember`, `explicit_constraint`, `explicit_decision`, `explicit_correction`, `explicit_forget`, and `accepted_proposal`. Retain exact payload Unicode; title is its first 80 Unicode scalars; tags empty; category `project` for project scope, otherwise `user`; dates null. Only actual user text supplies payload. Multiple directives, quoted/code-fenced text, hypothetical “if we decide,” ambiguous “forget that,” and vague assent produce `pending` with no mutation. Ordinary text yields an empty operation list, not a fabricated pending decision. Language outside this narrow grammar remains available through explicit operator controls in phase 4; never advertise generalized natural-language decision understanding.

Scope uses the phase 2 snapshot for automatic capture, never inferred from text/category or the currently selected UI Agent. Explicit user-wide capture uses the explicit scoped manual API; automatic capture does not elevate to user scope. A re-bound Session does not move old facts. Exact target IDs must belong to the captured scope; no fuzzy search deletes or supersedes multiple facts.

Generic `verified_observation` admission is deliberately unsupported in this phase. A successful `session_runs` row, tool success, output hash, check exit code, or model “verified” sentence alone cannot prove an arbitrary fact. Test rejection; retain actual runtime refs for diagnostics and future revalidation without introducing another verifier. A user-approved restatement is stored as `user_statement`.

| Turn state / terminal observation | Explicit user operation | Assistant/proposal/continuity behavior |
|---|---|---|
| completed | Commit eligible user operation and receipt | A staged proposal remains excluded until separate acceptance; never promote response prose |
| partial | Same user admission independent of inference result | No inferred decision or completion; preserve active objective |
| cancelled | Same user admission, including no assistant output | Preserve active objective; no skill change |
| failed / timed-out error mapped by phase 2 | Same user admission | Failure cannot establish a verified observation or completed objective |
| unterminated / Bun generation lost | Same immutable user admission during recovery | Terminal receipt states unterminated; preserve objective; no inferred assistant fact |
| prepared / invalidated / expired / unavailable with no start | Explicit recorded instruction may commit when caller/recovery requests capture; terminal status stays null until authoritative recovery marks it | No claim that inference completed, and no fabricated run ID |

Call capture after terminal/stream exit and on recovery, not between registration and stream consumption: a new capture mutation would correctly invalidate its own unconsumed preparation. `memory_capture_turn` first attempts private phase 2 sync; sync failure does not prevent explicit user admission from an existing immutable record, but produces observable `capture_unavailable` diagnostics and no assistant admission. SQLite/mutation-gate failure returns an error with no successful receipt. Save acknowledgement appears only after committed result, separately from assistant prose.

Operation identity is `(session_id,operation_id)`; automatic IDs are `turn/<turn_id>/user/0`, proposal acceptance reuses that user operation slot, and operator controls use fresh UUIDs. SHA-256 covers a fixed-version canonical array of operation kind, snapshot scope, source message ID/hash, target ID/revision, exact draft fields/reason. Persist the original successful response JSON. Identical retry returns the exact prior result without new rows/events/revision changes. Same identity/different payload returns `operation_conflict`; expected-revision failure writes no partial ledger. Canonical hashes exclude timestamps and nullable runtime run IDs.

For staged proposals include the immutable assistant-message ID/content hash in that canonical array; operator manual operations use their explicit request draft plus native-resolved scope and Session. `saved_count` counts only `saved`/`corrected` operations; `pending_count` counts only `pending`. A `blocked` operation never confirms saving. The receipt-state helper returns `failed` for a capture error or blocked-only receipt, `pending` for unresolved operations, `saved` only when committed saved_count is positive, otherwise `unchanged`.

One terminal capture receipt per `turn_id` additionally records the authenticated terminal tuple hash from phase 2 (status, bound IDs/hash, generation, terminal timestamps/run ID/evidence refs). Identical terminal replay is a no-op; conflicting terminal status/content or source binding rejects. A pre-terminal user-operation receipt can be augmented once by an authoritative terminal receipt without rerunning its mutations. Late success cannot replace an already finalized unterminated/cancelled receipt; record conflict for operator inspection. Same-turn repeated UI/relay/recovery calls share this ledger.
